# AI 编程产品出海提示词模板

> 适用场景：用 AI 编程做轻量级海外工具站、Web App、开发者工具、SEO 型小产品。
> 核心链路：找词 -> 竞品分析 -> PRD -> 开发 -> 修 Bug -> 上线 -> SEO 监控 -> 复盘迭代。

---

## 1. 新词机会判断

用于把候选关键词放进 Google Trends / 搜索结果后，让 AI 帮你判断是否值得做站。

```text
你是一个熟悉 AI 产品出海、SEO 和轻量级工具站的产品顾问。

我正在评估一个海外工具站关键词：

关键词：【填写关键词】
Google Trends 观察结果：
【填写 7 天 / 30 天 / 90 天趋势、是否为新词、和 GPTs 等基准词的对比】

Google 搜索结果观察：
【填写前 5 个结果类型：工具站 / 文章 / 社交媒体 / 新闻 / 论坛 / 软件页】

请帮我判断：
1. 这个词是否适合做轻量级工具站？
2. 它更像短期热点，还是可能沉淀成长尾需求？
3. 搜索这个词的用户最可能想完成什么任务？
4. 现在搜索结果页有没有明显空位？
5. 如果做，第一版 MVP 应该只解决哪个核心问题？
6. 哪些功能暂时不要做？
7. 合规、版权、隐私或安全风险是什么？

要求：
- 不要只给乐观判断，要明确指出不适合做的理由。
- 如果信息不足，请列出我还需要补充观察什么。
- 最后给出结论：值得做 / 暂缓 / 放弃。
```

## 2. 单个竞品网站分析

用于分析 Google 搜索结果里排名靠前的同类网站。

```text
你是一个经验丰富的产品经理，而我是一个准备使用 AI 编程做出海工具站的独立开发者。

请分析这个网站：

网站地址：【粘贴 URL】
目标关键词：【填写关键词】
我的观察：
【可选，填写你自己看到的页面、功能、体验问题】

请输出：
1. 这个网站的核心功能是什么？
2. 它满足了用户什么需求？
3. 它的 UI/UX 做得好的地方是什么？
4. 它明显的不足和可改进点是什么？
5. 用户在使用它时可能遇到哪些痛点？
6. 它的 SEO 页面结构有什么值得借鉴的地方？
7. 如果我要做同类产品，应该避开什么？

要求：
- 不要泛泛评价，要结合页面功能和用户任务分析。
- 重点关注可执行的差异化机会。
```

第一个网站：
"""

"""

第二个网站：
"""
【粘贴分析结果】
"""

第三个网站：
"""
【粘贴分析结果】
"""

请帮我输出：
1. 这类网站的共同功能是什么？

【填写】

【粘贴】

我决定保留的核心功能：
【填写】

我明确不做的功能：
【填写】

1. 产品一句话定位
2. 目标用户与使用场景
3. 核心用户流程

## 5. AI 编程执行总控

用于把 PRD 交给 Codex / Claude Code / Cursor / OpenCode 进行开发。

```text
你是一个经验丰富的独立开发者。

请先阅读项目文件夹中的 PRD 文档和现有项目结构，然后根据 PRD 进行开发。开发完成后，启动可访问的预览服务，并给我实际访问入口供我检查。

重要：不要在未完成需求澄清前直接写代码。

工作流程要求：

第一步：读取与澄清
- 先阅读 PRD 文档、项目目录、现有代码和配置文件。
- 在开发前，必须判断是否存在会影响实现的问题。
- 如果存在任何会影响功能范围、技术选型、用户体验、数据处理、合规风险、第三方服务、验收标准、运行方式的问题，必须暂停开发，先在对话中一次性列出《需要确认的问题清单》。
- 每个问题必须包含：
  - 问题：
  - 为什么需要确认：
  - 我的建议：
  - 可选项：
- 你必须等待我按编号回复后，才能开始开发。
- 不允许用“默认假设”“后续可调整”“先实现再说”绕过确认。
- 不允许把未确认问题写进代码、TODO 或最终说明里。
- 如果你判断没有阻塞性问题，先回复一句：
  “我没有发现需要先确认的阻塞问题，将按 PRD 直接开始开发。”
  然后再继续开发。

第二步：开发执行
- 严格按照 PRD 范围开发，优先完成核心功能，不擅自扩展非 MVP 功能。
- 如果 PRD 和现有代码冲突，以 PRD 为准；但如果冲突会造成明显风险，必须先问我确认。
- 尽量沿用项目已有技术栈、目录结构、组件风格和工程约定。
- 涉及隐私、合规、文件上传、第三方请求、数据存储时，必须严格遵守 PRD 的开发禁区。
- 不要实现 PRD 明确排除的功能。
- 不要引入不必要的重型依赖。
- 不要上传、保存或远程发送用户文件内容，除非 PRD 明确允许。
- 只要某个默认值会进入产品行为、UI 文案、数据处理、技术实现或验收标准，就必须先问我确认。
- 只有纯工程内部细节，且不影响用户体验、合规和 PRD 验收时，才可以自行选择。

第三步：验证与交付
- 开发完成后，必须进行基础自测。
- 如果项目有 build/test/lint 命令，优先运行相关命令并修复明显问题。
- 如果是前端项目，启动可访问的预览服务。
- 不要假设固定端口。
- 如果默认端口被占用，自动切换到可用端口。
- 如果是在远端服务器、容器、云开发环境或代理环境中开发，必须根据实际环境提供可访问的预览地址。
- 最后告诉我：
  - 已完成哪些功能
  - 是否有未完成或受限事项
  - 运行了哪些验证
  - 实际访问入口，例如本地 localhost 地址、局域网地址、远端预览地址、云开发环境 URL 或部署后的 URL
```

## 6. Bug 修复反馈

用于把截图、报错、操作步骤交给 AI 修复。

```text
你是负责这个项目的前端和全栈工程师。

我发现了一个 Bug，请按下面信息定位并修复：

页面 / 路由：
【填写】

复现步骤：
1. 【填写】
2. 【填写】
3. 【填写】

实际结果：
【填写】

期望结果：
【填写】

截图或报错信息：
【粘贴截图描述 / 控制台报错 / 网络请求失败信息】

请你：
1. 先复述你理解的问题。
2. 判断最可能的原因。
3. 阅读相关代码后再修改。
4. 修复时只改和这个 Bug 直接相关的代码。
5. 修复后运行必要验证。
6. 最后告诉我改了什么、怎么验证。

要求：
- 不要顺手重构无关代码。
- 如果信息不足，先问我，不要猜。
- 如果涉及布局问题，优先保证移动端和桌面端都不溢出、不遮挡。
```

## 7. GitHub 提交前脱敏检查

用于提交公开仓库前，让 AI 检查隐私、密钥和本机路径。

```text
请在提交到 GitHub 前，对当前项目做一次安全脱敏检查。

重点检查：
1. 是否存在 API Key、Token、Secret、Cookie、Webhook URL。
2. 是否存在我的个人信息、邮箱、手机号、真实姓名。
3. 是否存在本机绝对路径、用户名、公司项目路径。
4. 是否存在不应公开的测试数据或日志。
5. 是否存在 .env、配置文件、构建缓存、临时文件被错误提交。

请你：
1. 列出发现的问题。
2. 给出建议处理方式。
3. 修改 .gitignore。
4. 移除或替换敏感内容。
5. 完成后再提交代码。

如果发现任何高风险泄露点，先暂停提交并告诉我。
```

## 8. GitHub 仓库创建与提交

用于让 AI 辅助创建仓库、提交代码。

```text
目前项目开发基本完成，请将代码提交到 GitHub。

要求：
1. 提交前先执行安全脱敏检查。
2. 如果代码里有我的任何个人信息、本机路径、密钥、Token、环境变量，请彻底剔除或改为示例值。
3. 创建一个新的 GitHub 仓库。
4. 完成首次 commit 和 push。
5. 最后给我仓库地址。

如果有任何需要我授权或手动操作的步骤，请先告诉我，不要跳过。
```

目标关键词：【填写】

近 7 天点击：【填写】

## 12. 长尾词扩展与内页规划

用于从一个核心关键词扩展 SEO 内页。

```text
你是海外工具站 SEO 产品经理。

我的核心关键词是：【填写】
当前网站功能是：【填写】
当前用户主要需求是：【填写】

请帮我扩展长尾词和内页规划：
1. 给出 20 个长尾关键词。
2. 按用户意图分类。
3. 判断每个词适合做工具页、教程页、对比页、FAQ 页还是模板页。
4. 为优先级最高的 5 个词写页面标题和描述。
5. 说明这些内页如何反哺核心关键词权重。

要求：
- 避免堆砌关键词。
- 优先选择能承接真实用户任务的页面。
- 每个内页都必须有明确用途。
```

---

## 使用原则

1. 先找真实需求，再让 AI 写代码。
2. 每次开发前必须有 PRD，不要边聊边写。
3. 核心 PRD 定稿后，新开干净对话再进入开发。
4. 第一版只做一个核心功能。
5. 上线不是结束，GSC 数据监控才是验证开始。
6. 新词适合破冰，长期要转向老词里的长尾需求。
