# 三个最小工作流：告别多窗口切换的心力损耗

> 每次开发时在多个 AI 窗口之间来回切换，是开发者最大的隐性心力消耗。本章提供三个高信噪比的提示词模板，让你在一个窗口内完成需求拆解、代码复用和 BUG 排查。

---

## 为什么多窗口切换是结构性问题

多线程工作看起来效率高，实际上每次窗口切换都有隐性成本：

- **时间**：每次切换需要 2-5 分钟重新进入状态
- **心力**：认知资源被「记住每个窗口的进度」占据
- **质量**：每个窗口都处于浅层工作模式，做不到深度

一晚上切 5-6 次窗口，光是切换成本就可能吃掉 20-30 分钟。这不是个人效率问题，而是「多线程 + 上下文切换」的结构性缺陷。

---

## 解决方案：一个窗口，一条管道，一次完成

### 核心原则

> **每个工作流 = 一个完整的「输入 → AI 处理 → 人工校验 → 输出 → 沉淀」管道。不需要开第二个窗口。**

三个工作流不是三个 agent 窗口，而是**三种不同的高信噪比提示词模板**。一次只用一个，跑完一个任务就关上，然后打开下一个。

### 工作流设计铁律

1. **一个窗口跑到底**：这个窗口里的提示词模板已经包含了所有结构化的输出要求，不需要中途查资料、不需要新开窗口补充信息。
2. **输出即文档**：跑完直接产出可存档的文档，不是聊天记录，不是临时结论。
3. **跑完就沉淀**：每次跑完，有价值的输出直接存入知识库对应位置，下次直接搜，不用再跑一次。

---

## 工作流一：需求拆解（单窗口 15 分钟）

### 解决的问题

接到开发需求 → 大脑一片空白 → 不知道从哪开始 → 反复想 → 越想越乱

### 单窗口操作流程

```
步骤1：打开一个 Claude Code 窗口
步骤2：粘贴「需求拆解提示词模板」
步骤3：填入原始需求
步骤4：AI 输出结构化文档
步骤5：人工修改调整（5-10分钟）
步骤6：保存到项目目录 → 关窗口
```

**全程不需要开第二个窗口。不需要查资料、不需要问别的 agent、不需要来回对比。**

### 提示词模板（直接复制使用）

````markdown
你是一个资深产品经理兼技术架构师。请将以下开发需求拆解为结构化文档。

## 输入规则
- 如果需求描述模糊，先列出你的理解假设，让我确认后再继续
- 如果需求涉及多个模块，先画一个模块关系图再拆解
- 如果需求有技术风险，在风险点部分重点标注

## 输出格式（严格按此结构输出）

### 1. 需求背景
- 用户是谁？
- 在什么场景下遇到什么问题？
- 当前没有解决方案时用户怎么做（替代方案）？

### 2. 核心痛点
- 这个问题为什么重要（频次 × 痛苦程度）？
- 不解决会有什么后果？
- 解决了能带来什么价值（时间/金钱/体验）？

### 3. 技术方案
#### MVP 方案（1-2 周可完成）
- 核心功能：[一句话描述]
- 技术选型：[推荐技术栈，说明理由]
- 数据库设计：[核心表结构]
- API 设计：[核心接口，输入输出]

#### 完整版方案（后续迭代）
- 扩展功能：[列表]
- 技术优化：[列表]

### 4. 待办清单
按优先级排列，每项标注：
- 预估工时
- 前置依赖
- 完成标准

| 优先级 | 任务 | 预估工时 | 前置依赖 | 完成标准 |
|--------|------|----------|----------|----------|
| P0 | | | | |
| P1 | | | | |
| P2 | | | | |

### 5. 风险点
| 风险 | 概率 | 影响 | 应对方案 |
|------|------|------|----------|
| | 高/中/低 | | |

### 6. 验收标准
- [ ] 
- [ ] 

---

原始需求：
[在此粘贴]
````

### 跑完后做什么

输出直接存到 `07.项目管理/活跃项目/[项目名]/需求文档.md`。下次打开这个项目时，不需要重新拆解，直接看文档。

## 工作流二：代码复用（单窗口 5 分钟）

### 解决的问题

写了一段好用的代码 → 下次要用找不到了 → 重新写/AI重新生成 → 浪费时间且质量不稳定

### 单窗口操作流程

```
步骤1：写完一段可复用的代码
步骤2：在同一个 Claude Code 窗口中粘贴「代码沉淀提示词」
步骤3：AI 自动分类、打标签、生成搜索关键词
步骤4：复制输出，存入代码片段库
步骤5：继续写代码 → 不需要切换窗口
```

**关键思维转变**：代码沉淀不是「额外的工作」，而是「写完代码顺手做的事」。5 分钟而已。

### 提示词模板

````markdown
你是一个代码库管理员。请将以下代码片段分类、打标签，并生成可搜索的索引条目。

## 输出格式

### 分类
[工具类 / 业务逻辑 / API封装 / 数据库 / 中间件 / 测试 / 部署脚本 / 其他]

### 标签
格式：`#技术栈 #使用场景 #输入类型 #输出类型`
示例：`#Go #数据库迁移 #SQL文件 #自动建表`

### 搜索关键词
列出 5-10 个用户可能用到的搜索词，覆盖：
- 技术名词（如 gorm, postgres, migration）
- 使用场景（如 自动建表, 数据库初始化）
- 动词（如 生成, 迁移, 初始化）

### 代码摘要
一句话描述这段代码做什么。

### 输入/输出
- 输入：[参数/文件/数据格式]
- 输出：[返回值/文件/效果]

---

代码片段：
```[语言]
[在此粘贴]
```
````

### 跑完后做什么

输出直接存到 `06.构建工坊/代码片段库/[Go/Python等]/[功能描述].md`。

下次需要时，在知识库中搜索关键词，5 秒找到，不需要重新写、不需要开 agent 窗口。

## 工作流三：BUG 排查（单窗口 10-20 分钟）

### 解决的问题

遇到报错 → 盲目尝试 → 改了几处还是不行 → 越来越焦虑 → 一晚上过去了

### 为什么现在的方式低效

现在的「多窗口排查」模式：
- 窗口 A：看报错信息
- 窗口 B：搜解决方案
- 窗口 C：改代码
- 窗口 D：问 AI 可能的原因

四个窗口的信息没有汇总，你要靠大脑把它们串起来。这对心力是巨大的消耗。

### 单窗口操作流程

```
步骤1：遇到报错 → 复制完整报错信息（文本，不是截图）
步骤2：在同一窗口粘贴「BUG 排查提示词」
步骤3：附带报错位置的相关代码
步骤4：AI 输出结构化排查指南
步骤5：按步骤逐条排查，排查完一项打勾一项
步骤6：问题解决后，顺手沉淀为踩坑记录
```

**全程只用一个窗口。排查指南就是你的操作手册，你只负责执行和打勾。**

### 提示词模板

````markdown
你是一个资深全栈工程师，擅长快速定位和修复 bug。

## 排查原则
- 从最简单的原因开始排查，不要一开始就怀疑底层框架
- 每给出一个排查步骤，说明「如果结果是什么，说明什么」
- 如果信息不足，明确指出还需要什么信息，不要猜测

---

## 报错信息（完整粘贴）
```
[在此粘贴完整报错，包括 stack trace]
```

## 相关代码
```[语言]
[粘贴报错位置所在函数/方法的完整代码]
```

## 运行环境
- 操作系统：
- 语言/框架版本：
- 最近改动：[最近改了什么相关代码]

---

1. **原因 A**（概率：X%）

   - 如果是这个原因，报错会出现的特征：

| 步骤 | 操作 | 预期结果 | 如果不符合预期，说明什么 | 完成 |
|------|------|----------|------------------------|------|
| 1 | | | | ☐ |
| 2 | | | | ☐ |
| 3 | | | | ☐ |

### 最可能的解决方案
```[语言]
[具体修复代码]
```

### 预防措施
- [ ] 如何避免再次出现此问题：
````

### 排查完成后做什么

1. 如果是一个有价值的坑 → 用以下简版模板存入 `09.方法论沉淀/踩坑记录/`：
```markdown
# [技术/产品]-问题简述
## 症状
## 原因
## 解决方案
## 预防
```
2. 如果只是一个小疏忽 → 不用存，继续干活。

**判断标准**：这个问题你以后还可能遇到吗？yes → 存。no → 不存。

## 心力分配对比

| | 多窗口模式 | 单窗口+工作流模式 |
|---|---|---|
| 窗口数 | 3-4 个 | 1 个 |
| 上下文切换次数 | 每 10-15 分钟一次 | 0 次 |
| 心力消耗 | 大量消耗在「记住进度」 | 全部用在「执行」 |
| 可沉淀产出 | 聊天记录（散） | 结构化文档（可复用） |
| 下次启动成本 | 重新回忆上下文 | 打开文档就续上 |

---

## 让工作流真正跑起来的落地策略

### 第一步：今晚只搭一个（选最痛的那个）

不要三个一起搭。选一个你今晚最需要的：

| 工作流 | 适合的场景 | 首次搭建时间 | 第一个产出 |
|--------|-----------|-------------|-----------|
| 需求拆解 | 手上正好有需求要拆 | 15 分钟 | 一份需求文档 |
| 代码复用 | 刚写完一段好代码 | 5 分钟 | 一个代码片段条目 |
| BUG排查 | 正被一个 bug 卡住 | 10 分钟 | 排查指南 + bug 修复 |

**选一个，今晚就跑一次。跑通了就有第一个成功案例。三天跑通三个。**

### 第二步：每个工作流跑 3 次再优化

第一次跑：看流程顺不顺，哪里卡住。
第二次跑：微调提示词，去掉多余步骤，补充缺失步骤。
第三次跑：确认稳定 → 这就是你的「1.0 版本工作流」。

三次跑完后，你不再需要「记住工作流怎么操作」，它会变成肌肉记忆。

### 第三步：从提示词模板升级为 Skill

当一个工作流跑了 5 次以上且步骤稳定后，把它升级为 Skill：

```text
~/.agents/skills/requirement-breakdown/SKILL.md
~/.agents/skills/code-reuse/SKILL.md
~/.agents/skills/bug-troubleshoot/SKILL.md
```

升级成 Skill 后，你只需要说一句「帮我拆解这个需求」，AI 自动加载完整工作流，连提示词都不用贴。

---

## 核心心法

> **工作流不是一套「更聪明的提示词」，而是一套「不用思考就能执行的管道」。**
>
> 它的价值不在于「AI 输出质量提高了 20%」，而在于「你不需要思考接下来该做什么」。
>
> 最好的工作流是你用了几次之后就感觉不到它的存在——它变成了你做事的自然方式。

---

## 检查清单：一个工作流是否真的在帮你省心力

用以下问题检验每个工作流：

- [ ] 运行时不需要新开 agent 窗口？
- [ ] 从「有输入」到「有可存档输出」一气呵成？
- [ ] 中间不需要「等一下我查个东西」？
- [ ] 跑完 3 次后不需要看提示词模板？
- [ ] 输出可以直接存入知识库，不需要重新整理格式？

三个都是 ✅ → 这个工作流真的在省心力。
有一个 ❌ → 找到卡点，下一版修复。
