# AI 代码理解工作流：快速定位并理解 AI 生成的代码

> AI 辅助开发中，最大的风险不是 AI 写不出代码，而是上线出 bug 时你面对的是自己不熟悉的代码。这个工作流帮你在关键时刻快速重建对任何一段代码的完整理解。

---

## 问题定义

### 一个典型场景

```
你在做一个复杂需求，AI 帮你写了 80% 的代码。
五个 agent 窗口，几十轮对话，代码散落在多个文件里。

上线那天，流量一上来，服务挂了。
日志显示：goroutine 数量暴涨 → 死循环。

你打开代码，看着 AI 写的逻辑，大脑一片空白：
- 这段代码是谁写的？某个 agent 写的。
- 它为什么这么写？当时大概觉得合理。
- 哪里可能死循环？不知道，得从头读。

但你没有从头读的时间。线上正在挂。
```

### 根因分析

```
AI 替你写了代码，但没有替你在脑子里建「代码心智模型」。

传统开发：你亲手写每行代码 → 脑子自然有地图
AI 辅助开发：AI 写了很多代码 → 你只负责 merge → 脑子是空的

上线前：代码能跑 = 没问题（危险假设）
上线后：出了问题 = 不知道从哪查（致命后果）
```

**这个工作流要解决的就是：在需要的时候（排查 bug、准备上线、接手旧代码），用 AI 帮你快速重建对一段代码的完整理解。** 不是让 AI 帮你写新代码，而是让 AI 帮你读懂已有的 AI 代码。

---

## 核心原则

### 一个窗口，一份文档，一次理解

```
输入：一个需求名 / 一个功能名 / 一个 bug 描述
输出：一份「代码地图」文档，包含：
  - 这段需求的完整代码在哪
  - 每段代码干什么（用你自己的语言解释）
  - 逻辑流程图
  - 潜在风险点（并发、死循环、边界条件）
  - 我以后怎么快速找到它

全程一个 agent 窗口。不需要来回切。
```

### 和「代码复用工作流」的区别

| | 代码复用工作流 | AI 代码理解工作流 |
|---|---|---|
| **目的** | 把好代码存起来以后用 | 把 AI 写的代码读懂、找得到 |
| **时机** | 写完代码顺手做 | 要排查问题 / 准备上线前 / 接手一段不熟悉的代码 |
| **输入** | 一段代码片段 | 一个需求名 / 功能名 / 关键词 |
| **输出** | 分类标签索引 | 代码地图 + 逻辑解释 + 风险标记 |
| **解决的问题** | 「这段好代码在哪？」 | 「这段代码是什么意思？哪里可能出 bug？」 |

## 工作流：从需求名到完整代码理解的单窗口管道

### 操作步骤总览

```
步骤1：确定你要理解什么（需求名/功能名/关键词）
步骤2：在当前 Claude Code 窗口中粘贴工作流提示词
步骤3：AI 搜索代码库 → 定位相关代码 → 解释逻辑 → 标记风险
步骤4：人工核对 AI 的解释是否正确（关键步骤！）
步骤5：输出「代码地图」文档 → 存入项目目录
步骤6：以后需要时，打开文档 30 秒找到目标代码
```

### 步骤详解

#### 步骤1：确定理解目标

不需要精确的文件名或函数名，只需要你能说出来的描述：

- ✅「用户下单后扣库存的逻辑」
- ✅「支付回调处理」
- ✅「导出报表那块的代码」
- ✅「上次那个死循环的并发逻辑」
- ❌ 不需要知道 `order_service.go` 的 `func DeductStock()`

#### 步骤2-3：粘贴提示词模板，让 AI 去搜索

**核心提示词模板**（直接复制使用）：

````markdown
你是一个资深代码审查员，擅长快速理解陌生代码库并建立逻辑地图。

## 任务
帮助用户定位并理解一个功能/需求的所有相关代码。用户可能不记得代码在哪，只知道大概做了什么。

## 用户要理解的功能
[在此描述：需求名 / 功能描述 / 你记得的关键词]

## 执行步骤

### 第1步：全局搜索定位
在代码库中搜索所有相关代码。搜索策略：
- 搜索功能关键词（中文注释、变量名、函数名）
- 搜索相关的 API 路由
- 搜索相关的数据库表名
- 搜索错误信息字符串

输出你找到的所有相关文件和位置。

### 第2步：逐文件解释
对每个相关文件，用**用户能理解的语言**解释：
- 这段代码负责什么？（一句话）
- 输入什么？输出什么？
- 关键逻辑分几步？
- 这个文件里的代码有没有被其他代码调用？在哪里调用？

### 第3步：绘制调用链
按数据流的顺序，画出完整的调用链：

```
请求入口（HTTP Handler / RPC / 消息队列）
  → 业务逻辑层（Service）
    → 数据访问层（Repository / DAO）
      → 数据库操作
    → 外部调用（API / MQ / Cache）
  → 返回结果
```

标注每层的文件路径和函数名。

### 第4步：标记风险点 🔴
重点检查以下风险：
- **并发风险**：有没有共享变量没加锁？有没有 map 并发读写？goroutine 有没有正确退出？
- **死循环风险**：for/while 循环的退出条件是否一定会满足？递归有没有终止条件？
- **边界条件**：空值、零值、空数组、超大数据量时会不会崩？
- **错误处理**：error 有没有被忽略？（Go 中 `_ = err` 或直接不接收 error）
- **资源泄漏**：数据库连接、HTTP 连接、goroutine 有没有正确关闭？

每个风险标注：
| 位置 | 风险类型 | 风险描述 | 严重程度 | 触发条件 |
|------|---------|---------|---------|---------|

### 第5步：生成查找索引
为这个功能生成一张「以后怎么找」的索引表：

| 我想找什么 | 关键词搜索 | 文件路径 | 函数名 |
|-----------|-----------|---------|--------|
| [场景] | [搜什么] | [在哪] | [哪个函数] |

---

现在开始执行。先告诉我们代码库的语言和技术栈，然后按步骤执行。
````

#### 步骤4：人工核对（最关键的一步）

AI 给你解释后，你必须做一件事：**打开代码，对照 AI 的解释，确认它没胡说。**

```
核对清单：
□ AI 说的调用链是否和代码一致？
□ AI 解释的逻辑是否和代码的实际行为一致？
□ AI 标记的风险是否真实存在？（不是所有风险都会触发）
□ AI 有没有遗漏关键文件？（对照 git log 看看涉及了哪些文件）
```

**这一步不能省。** AI 可能在解释代码时产生幻觉。你不需要读懂全部代码——你只需要判断「AI 说的这段描述」和「你看到的这段代码」能不能对上。

#### 步骤5：输出文档

将 AI 的输出（核对修改后）保存为项目代码地图文档。

#### 步骤6：以后怎么用

```
场景：线上告警「导出报表超时」

不用从头读代码。打开「导出报表-代码地图.md」
  → 看调用链 → 定位到数据查询层
  → 看风险标记 → 「超大数据量时可能慢查询」已被标记
  → 直接去排查慢查询 → 10 分钟定位，而不是 2 小时
```

## 专项场景：上线前的「AI 代码安全检查」

> 这是针对你「AI 拼凑代码上线后死循环」经历专门设计的检查流程。

### 触发时机

每次你准备上线一个「大部分代码由 AI 生成」的需求时，跑一遍这个检查。

### 检查提示词

````markdown
你是一个代码安全审查员，专门审查 AI 生成的代码在上线前的风险。请对以下代码进行安全检查。

## 要检查的代码范围
[粘贴文件路径列表，或描述需求范围]

## 重点检查项目（按优先级）

### P0 - 会导致服务挂掉的问题
1. **死循环**：所有 for/while 循环是否有确定会触发的退出条件？
2. **goroutine 泄漏**：每个 go func() 是否有对应的退出机制？有没有用 context 控制生命周期？
3. **锁死锁**：Mutex/RWMutex 的 Lock 是否有对应的 Unlock？有没有跨函数加锁？
4. **空指针/nil 引用**：所有指针、map、slice 使用前是否已初始化？
5. **数组越界**：所有 slice/array 访问是否检查了长度？

### P1 - 会导致数据错误的问题
6. **并发写 map**：Go 中 map 是否在并发场景下使用了 sync.Map 或加了锁？
7. **竞态条件**：多个 goroutine 对同一变量的读写是否有正确的同步？
8. **事务边界**：数据库事务是否正确处理了回滚？嵌套事务是否合理？
9. **幂等性**：支付、扣库存等操作在高并发下是否会重复执行？

### P2 - 会导致性能问题的问题
10. **慢查询**：数据库查询是否用了合适的索引？有没有 N+1 查询？
11. **大对象内存**：有没有一次性加载全部数据到内存的操作？
12. **未设置超时**：HTTP 请求、数据库连接、RPC 调用是否设置了超时？

---

## 输出格式

### 发现的问题
| 优先级 | 位置 | 问题类型 | 问题描述 | 修复建议 | 修复代码 |
|--------|------|---------|---------|---------|---------|
| P0 | | | | | |

### 统计
- P0 问题：[N] 个 → 必须在上线前修复
- P1 问题：[N] 个 → 建议在上线前修复
- P2 问题：[N] 个 → 可上线后迭代修复

### 总体评估
- [ ] 可以上线（P0 全部修复）
- [ ] 不建议上线（存在未修复的 P0 问题）
````

### 使用方式

```
1. 上线前 1-2 天，确定要上线哪些代码
2. 跑这个检查工作流
3. P0 问题必须修完
4. P1 问题评估是否阻塞上线
5. P2 问题记入 backlog
```

**这个检查不能替代代码审查，但它能帮你避免「AI 写了死循环你没发现就上线了」这种级别的灾难。**

## 日常使用：需求代码地图索引

### 每完成一个需求后做的事

不用每次排查 bug 才跑工作流。每完成一个需求就生成一份「代码地图」，存入项目目录。

```
07.项目管理/活跃项目/[项目名]/
  ├── 需求文档.md
  ├── 代码地图/                    ← 新建这个目录
  │   ├── 用户下单-代码地图.md
  │   ├── 支付回调-代码地图.md
  │   └── 导出报表-代码地图.md
  └── 上线检查/
      ├── 2026-06-07-用户下单上线前的安全检查.md
      └── ...
```

### 代码地图文档的模板

```markdown
# [需求名] - 代码地图

> 生成时间：2026-06-07
> 涉及技术栈：Go + Gin + GORM + MySQL + Redis

## 功能概述
[一句话描述这个需求做什么]

## 调用链
```
POST /api/order/create → OrderHandler.Create()
  → OrderService.CreateOrder()
    → StockService.DeductStock()  // 扣库存
      → Redis: DECR stock_key     // 先扣 Redis
      → MQ: stock_change_event    // 发消息异步同步到 DB
    → OrderRepo.Insert()          // 写订单表
    → PaymentService.CreatePay()  // 调支付
```

## 关键文件
| 文件 | 作用 | 关键函数 |
|------|------|---------|
| handler/order.go | 处理 HTTP 请求，参数校验 | Create(), List() |
| service/order.go | 订单业务逻辑 | CreateOrder(), CancelOrder() |
| service/stock.go | 库存扣减 | DeductStock(), RollbackStock() |
| repo/order_repo.go | 订单数据库操作 | Insert(), UpdateStatus() |

## 风险标记
| 风险点 | 位置 | 说明 |
|--------|------|------|
| 并发扣库存 | service/stock.go:DeductStock() | 用 Redis DECR 保证原子性，但异步同步 DB 可能丢失 |
| 支付超时 | service/order.go:WaitPay() | 已设 30 分钟超时，超时后自动取消 |

## 快速查找索引
| 我想找 | 搜索关键词 | 文件 |
|--------|-----------|------|
| 扣库存逻辑 | DeductStock, stock | service/stock.go |
| 订单创建流程 | CreateOrder | service/order.go |
| 支付回调 | PayCallback, notify | handler/payment.go |
```

**四个工作流形成闭环**：拆 → 写 → 理解 → 查 → 沉淀。不需要开多个 agent 窗口。
