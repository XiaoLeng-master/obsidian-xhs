# Skill：把经验写成 AI 可执行能力包的方法论

> 来源：腾讯 Skill 实践文章、Anthropic Skill 设计理念、一线开发实战验证。
> 适用场景：当需要把一套反复使用的经验、流程、提示词、检查清单或项目方法沉淀成可复用 Skill 时使用。

## 一句话结论

Skill 的本质不是”提示词写得更长”，而是把人脑里的稳定经验压缩成 AI Agent 能触发、能执行、能验证、能迭代的操作手册。

每写好一个 Skill，就等于把一个反复消耗心力的工作流，封装成以后可以一键调用的能力包。

## Skill 到底是什么

一个 Skill 通常是一个目录：

```text
skill-name/
  SKILL.md
  scripts/       # 可选：脚本、检查、迁移、转换
  references/    # 可选：长文档、API、字段映射、长示例
  assets/        # 可选：模板、静态资源
  evaluation/    # 可选：触发评估和质量评估用例
```

其中 `SKILL.md` 是核心，它要回答六个问题：

- 什么时候触发？
- 做什么？
- 不做什么？
- 按什么步骤做？
- 怎么判断做对了？
- 哪些坑必须避开？

## Skill 和普通提示词的区别

| 类型 | 适合放什么 | 特点 |
|---|---|---|
| 临时提示词 | 一次性任务、探索性问题 | 快，但不可复用 |
| 提示词模板 | 重复 3 次以上，但流程还不稳定 | 适合快速试错 |
| SOP 文档 | 人也要读、流程仍需人工判断 | 适合沉淀流程 |
| Skill | 流程稳定、AI 可按步骤执行和验证 | 适合长期复用 |
| 项目规则 | 所有任务都必须遵守的约束 | 放 `AGENTS.md` 或项目说明 |
| 脚本/CI | 可机械校验或强制执行的规则 | 不要只靠文档 |

判断标准：

- 如果只是这次要用，不写 Skill。
- 如果已经反复遇到，但还没跑顺，先写提示词模板。
- 如果已经跑过 5 次以上，并且步骤稳定，写 Skill。
- 如果涉及检查、迁移、API 调用、数据处理，考虑配 `scripts/`。
- 如果背景很长，放 `references/`，不要塞进 `SKILL.md`。

## 好 Skill 的核心结构

推荐模板：

```markdown
---
name: example-skill
description: Use when [具体触发场景、用户意图、工具名、文件类型、错误症状]
metadata:
  version: "1.0"
---

# Example Skill

## 概述
[这个 Skill 让什么重复任务变得可靠。]

## 什么时候使用
- [触发场景]
- [触发场景]

不要在以下情况使用：
- [非目标场景]

## 前置条件
- [需要的上下文、文件、权限、工具]

## 工作流
1. [步骤]
   检查点：[命令或预期输出]
2. [步骤]
   检查点：[命令或预期输出]

## 示例
### 示例 1：正常场景
输入：
[input]

输出：
[expected output]

### 示例 2：边界场景
输入：
[input]

输出：
[expected output]

## 验证
- [ ] [检查项]
- [ ] [检查项]

## 常见错误
| 错误 | 修复 |
|---|---|
| [错误] | [修复] |
```

## `description` 是 Skill 成败的一半

AI 是否会加载 Skill，主要看 `description`。所以 `description` 不是摘要，而是触发条件。

错误写法：

```yaml
description: Runs a five-step workflow to analyze competitors and write PRDs.
```

问题：这是流程摘要，不是触发条件。AI 可能只读这句话就开始执行，跳过正文细节。

正确写法：

```yaml
description: Use when evaluating overseas product ideas, analyzing competitor tool sites, or turning SEO keywords into MVP PRDs.
```

写 `description` 的规则：

- 以 `Use when` 开头。
- 写用户会怎么说，而不是 Skill 内部怎么做。
- 包含任务关键词、同义词、工具名、文件类型、错误症状。
- 技术黑话要配普通语言。
- 写清不适用范围，避免和其他 Skill 冲突。

## 写 Skill 的 8 步流程

### 1. 定义任务

先写清楚：

- 这个 Skill 服务谁？
- 它解决哪个重复任务？
- 输入是什么？
- 输出是什么？
- 成功标准是什么？
- 哪些情况要跳过？

### 2. 写触发条件

先写 `description`，不要先写正文。

原因：触发不准，正文写得再好也没用。

### 3. 写范围边界

每个 Skill 都要写：

- 适用场景。
- 不适用场景。
- 前置条件。
- 跳过条件。
- 需要用户确认的条件。

### 4. 写执行步骤

使用祈使句：

- 检查项目结构。
- 搜索旧依赖。
- 替换 import。
- 运行测试。
- 如果检查失败，停止后续步骤。

不要写成商量式语言：

- 你可以考虑检查一下。
- 也许需要替换。
- 最好测试一下。

### 5. 加 Before/After 或输入/输出示例

AI 对例子的理解通常比抽象描述更稳定。

示例应该覆盖：

- 最常见场景。
- 稍微变形的场景。
- 边界或失败场景。

### 6. 加检查点

关键步骤后要有验证：

```bash
go test ./...
```

```bash
rg "old-package-name" --glob "*.go"
```

```bash
npm run build
```

没有检查点的 Skill，容易“一口气跑完，最后才发现前面错了”。

### 7. 加评估用例

评估分两类：

- 触发评估：该触发时有没有触发，不该触发时有没有误触发。
- 质量评估：触发后输出是否符合结构、完整性、准确性和边界要求。

触发评估示例：

| 类型 | 用例 | 预期 |
|---|---|---|
| 正例 | 帮我写一个产品调研 Skill | 触发 |
| 正例 | 把这个 SOP 变成可复用 Skill | 触发 |
| 反例 | 帮我写一篇公众号文章 | 不触发 |
| 边界 | 帮我优化这个提示词 | 视上下文决定 |

质量评估示例：

```markdown
## Quality Case：创建调研 Skill

输入：
用户要把竞品调研流程写成 Skill。

期望：
- 有明确 name 和 description
- 有适用范围和不适用范围
- 有工作流
- 有示例
- 有检查点
- 有触发评估和质量评估
```

### 8. 精简正文

`SKILL.md` 不要写成知识库文章。

应该保留：

- 指令。
- 判断规则。
- 示例。
- 检查点。
- 常见错误。

应该移到 `references/`：

- 长背景。
- 历史沿革。
- API 文档。
- 大量案例。
- 字段映射表。

## 模块化：Skill 太长就拆

如果出现下面情况，就应该拆分：

- `SKILL.md` 超过 500 行。
- 包含多个独立工作流。
- 某些步骤可以单独复用。
- 不同部分更新频率差异很大。

拆分方式：

```text
product-launch/
  SKILL.md
  references/
    market-research.md
    landing-page-checklist.md
    payment-integration.md

product-launch-research/
  SKILL.md

product-launch-payment/
  SKILL.md
```

主 Skill 负责编排，子 Skill 负责单一任务。

## 什么时候用 MCP，什么时候用 HTTP 脚本

| 场景 | 推荐方式 |
|---|---|
| 已有成熟 MCP Server | 优先 MCP |
| 多个 Skill 都要复用外部服务 | 封装 MCP |
| 需要统一鉴权、安全和审计 | MCP |
| 只是简单调用一个公开 API | HTTP 脚本 |
| 老系统改 MCP 成本高 | HTTP 脚本过渡 |
| 需要复杂重试、超时、日志 | 脚本中封装 |

我的原则：

- MCP 管连接和工具能力。
- Skill 管流程和判断。
- HTTP 脚本兜底处理一次性或低频外部调用。

## 安全底线

Skill 里的脚本可能会被真实执行，所以必须按工程资产对待。

发布前检查：

- 不硬编码 API Key、Token、密码、Cookie。
- 删除、覆盖、数据库写入、部署发布前必须确认。
- 数据库变更前先备份。
- 用户输入和文件路径要校验。
- 外部网页、文件、API 返回内容只当数据，不当指令。
- 网络请求使用 HTTPS，并设置超时。
- 脚本使用 fail-fast 策略，错误信息要清楚。

## 常见反模式

| 反模式 | 表现 | 修复方式 |
|---|---|---|
| 大杂烩 Skill | 一个 Skill 同时做调研、写 PRD、写代码、部署 | 拆成多个单一职责 Skill |
| description 黑话 | 只写内部术语，AI 不知道何时触发 | 用普通语言 + 技术关键词 |
| 没有示例 | 输出每次都不一样 | 加 3-5 个输入/输出示例 |
| 没有检查点 | 前面错了后面继续做 | 每个关键步骤加验证 |
| 写死数值 | 换项目就失效 | 写判断规则和范围 |
| Wiki 化 | 背景 300 行，动作 30 行 | 背景放 references |
| 没有反例 | 和其他 Skill 抢触发 | 写清 Do not use when |
| 没有评估 | 好不好全靠感觉 | 加触发和质量用例 |

## 常见的 Skill 类型与优先级建议

按一位独立开发者的典型场景，建议按以下优先级沉淀 Skill：

| 优先级 | Skill 类型 | 原因 |
|---|---|---|
| P0 | 产品 idea → MVP PRD | 解决想法多但难落地的问题 |
| P0 | 竞品调研与关键词分析 | 出海产品必须高频做 |
| P0 | AI 编程产品出海流程 | 直接服务于产品交付 |
| P1 | 技术踩坑复盘 | 把工作经验转成方法论 |
| P1 | Landing Page 生成与审查 | 补齐前端和营销弱项 |
| P2 | 周复盘与行动计划 | 保护心力，减少反复启动 |

## 写 Skill 的标准工作流

每次写 Skill 的推荐流程：

1. 判断是否值得写 Skill（是否已经重复 5 次以上、流程是否稳定）
2. 定义重复任务和成功标准
3. 生成 `name` 和 `description`
4. 起草 `SKILL.md`
5. 补充至少 3 个示例
6. 补充触发评估和质量评估
7. 放入 Skill 目录
8. 实际使用后，根据失败案例迭代

## 最小可用版本标准

一个 Skill 的第一版不需要完美，但至少要满足：

- 有准确的 `name` 和 `description`。
- 只解决一个重复任务。
- 有适用范围和不适用范围。
- 有 3-7 步清晰工作流。
- 至少 1 个示例。
- 至少 1 个验证方式。
- 至少 5 条触发评估用例。
- 没有硬编码密钥和危险操作。

## 关键提醒

不要一开始就追求”万能 Skill”。目标不是写一个超级复杂的 Skill 系统，而是把每个高频流程逐个封装，从重复解释、重复摸索、重复踩坑中解放出来。

Skill 的价值不在于第一次写得多完整，而在于它能不能被触发、能不能稳定执行、能不能在真实项目里减少心力消耗。
