> **一句话**：重要产出（代码、方案、文档）在交付之前，必须经过「生成 → 挑战 → 裁决 → 修正」的辩论环。不让一个人（或一个 Agent）独自决定什么是"对的"。

---

## 适用场景

| 场景 | 触发条件 |
|------|---------|
| 🏗️ **技术方案评审** | 任何产品方案/技术方案定稿前 |
| 💻 **核心代码审查** | 涉及支付、权限、数据安全、核心业务逻辑 |
| 📝 **重要文档** | PRD、技术文档、对外发布的方案 |
| 🚀 **上线前检查** | 首次部署或大版本发布前的最终检查 |

---

## 标准流程（5 步辩论环）

```
┌─────────────────────────────────────────────────────┐
│                    辩论式审查 SOP                     │
├──────────┬──────────────────────────────────────────┤
│ 第 1 轮  │ 生成方：产出初稿（方案/代码/文档）            │
│ 第 2 轮  │ 挑战方：系统性攻击——找漏洞、反例、边界条件     │
│ 第 3 轮  │ 生成方：逐条回应，修正或驳回                   │
│ 第 4 轮  │ 挑战方：对修正后的版本再次攻击                 │
│ 第 5 轮  │ 仲裁方：裁决剩余分歧，输出最终版本             │
├──────────┴──────────────────────────────────────────┤
│ 硬规则：最多 3 轮辩论。3 轮后仍有分歧 → 交人裁决。        │
└─────────────────────────────────────────────────────┘
```

## 角色定义

### 🔵 生成方（提案方）
**角色设定**：「你是一名经验丰富的开发者，任务是产出高质量、可落地的方案。你需要用清晰的逻辑和证据支撑你的每个决策。」

- 产出初稿
- 在第 3 轮对挑战逐条回应
- 标注修正了什么、驳回了什么及原因

### 🔴 挑战方（反对方）
**角色设定**：「你是一名专注于风险审查的资深审核员。你的任务不是提出替代方案，而是用最严格的标准系统性地检验方案的每个环节。保持职业怀疑态度。」

**攻击维度清单**：
- [ ] 逻辑漏洞：前后矛盾、因果跳跃、循环论证
- [ ] 事实错误：数据来源不可靠、假设不成立
- [ ] 边界遗漏：极端情况、边界输入、并发场景
- [ ] 安全风险：权限漏洞、数据泄露、注入攻击
- [ ] 性能隐患：N+1 查询、内存泄漏、阻塞调用
- [ ] 依赖风险：外部服务单点、API 限流、版本过期
- [ ] 成本盲区：Token 消耗、云服务费用、第三方服务计费

### ⚪ 仲裁方（法官）
**角色设定**：「你是一名技术负责人。双方各执一词时，你需要基于事实和工程原则做出最终裁决。不追求完美，追求在当前约束下的最优解。」

**裁决原则**：
- 安全相关 → 从严
- 性能相关 → 看数据（没有 benchmark 的争论不裁决）
- 风格相关 → 服从团队规范
- 不确定的 → 标注为已知风险，不阻塞发布

## 使用时可以这样给 Agent 下指令

**启动辩论**：
```
我需要你审查这个技术方案。先由 Agent A 生成初稿，
然后由 Agent B 以挑战方身份系统性攻击方案中的漏洞。
攻击维度包括：逻辑、安全、性能、边界条件、成本。
辩论 3 轮后，我来做最终裁决。
```

**仅做安全性辩论**：
```
使用辩论式审查 SOP，但只聚焦安全维度。
挑战方专攻：权限模型、数据泄露风险、注入漏洞。
```

---

## 关键设计原则

1. **法官模型必须强于辩论双方**：如果用的是同一个模型，仲裁质量无法保证
2. **3 轮硬上限**：辩论容易无限循环，给轮数设限，剩余分歧交人裁决
3. **挑战方只管攻击，不管建设**：如果挑战方同时负责"给出替代方案"，攻击就不够纯粹
4. **可以接入外部知识库**：挑战方在攻击事实性错误时，可以实时搜索外部数据作为反驳依据
